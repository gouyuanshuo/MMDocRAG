# 论文式基线：逐项核对

> 目的：在声称任何「相对已发表工作的改进」之前，先逐项核对本地基线与
> MMDocRAG 论文（arXiv 2505.16470）所用系统的差异。凡对不上的项，
> 提升只能表述为**相对本地替代基线**而言。
>
> 核对日期 2026-08-30。论文事实取自 arXiv HTML 版正文与 Table 6。

## 一、逐项对照

| 维度 | 论文 | 本项目现状 | 判定 |
|---|---|---|---|
| 文本检索器 | **「BGE」，未给出版本或 HF id** | `BAAI/bge-small-en-v1.5` | ⚠️ 不可判定是否一致 |
| 视觉检索器 | **「ColQwen」，未给出版本** | `vidore/colqwen2-v1.0`，本地 LoRA + Qwen2-VL base | ⚠️ 同上，但**确为真视觉检索** |
| 视觉候选表示 | 原始图片像素 | 原始图片像素（MaxSim 后交互） | ✅ 一致 |
| 配额 k=10 | 7 文本 / 3 图片 | 7 / 3 | ✅ |
| 配额 k=15 | 10 / 5 | 10 / 5 | ✅ |
| 配额 k=20 | 12 / 8 | 12 / 8 | ✅ |
| **文本池规模** | **536 quote/doc** | 自建 chunk **421/doc**（`retrieval/quotes.sqlite`，92,752 条） | 🟡 79%，量级相当 |
| **图片池规模** | **63 quote/doc**（≈13,860） | **29.8/doc**（官方候选并集） | ❌ **47%，主要缺口** |

## 二、两条必须更正的先前表述

1. **论文没有指定任何检索器的版本。** 先前把「bge-large-en-v1.5 与
   ColQwen2-v0.1」说成论文配置，是我的推断而非论文原文。正确说法是：
   论文只写了模型族名（BGE、ColQwen），**版本不可复现地确定**。
   因此换用 bge-large 只能表述为「更接近论文规模的文本检索器」，
   **不能**表述为「与论文版本一致」。

2. **ColQwen 早已是真的。** `models/colqwen2-v1.0` 与
   `models/colqwen2-base` 已在本地，`retrieval/colqwen_index.py` 走
   `.venv-colpali` 跑 MaxSim 后交互、直接读图片像素，产出 69,842 条排名。
   视觉侧**不是**替代品，先前「需要下载 ColQwen」的说法不成立。

真正的主要缺口是**图片池规模**，不是模型身份。

## 三、图片池扩张的陷阱：描述覆盖率

220 篇 evaluation 文档在磁盘上共 **13,999 张图 = 63.6/doc**，与论文的 63/doc
吻合。但其中**只有 5,056 张（36.1%）带 VLM 描述**——描述只存在于官方候选池里。

这决定了扩池**不能对两个分支同时做**：

| 分支 | 表示 | 可覆盖的图片 |
|---|---|---|
| ColQwen | 图片像素 | **13,999（全部）** |
| BM25 / BGE over `img_description` | VLM 文字描述 | 5,056 |

天真地把池扩到 13,999，等于让 ColQwen 面对 13,999 个干扰项、
而描述分支只面对 5,056 个。**那会单方面压低 ColQwen，制造出本方法的假胜。**
方向与先前的偏置相反，但同样是错的。

因此必须拆成两个互不替代的测量：

- **(A) 论文可比的绝对 recall**：ColQwen 在完整 13,999 池上。
  这个数才可以与论文 Table 6 的 ColQwen 行（R@20 img = 84.3）并列，
  用途是**验证本地 ColQwen 实现是否落在正确量级**。描述分支不参与。
- **(B) 公平的配对比较**：两分支同池。目前只能在 5,056 张带描述的图上做，
  即现状。绝对值相对论文偏高（干扰项少），但**两臂同池，配对内部效度成立**。

要让描述分支也上全池，需要为 8,943 张图补 VLM 描述——那是一次带图的
生成调用，属于付费项，**不在本轮范围内，需单独批准**。

## 四、实测：把文本检索器换成 bge-large 之后

两个池 × 两个 k，其余全部固定（同一批题、同一 gold、同一视觉臂、同一配额、
同一 document-cluster bootstrap，B=4000）。`*` 表示 95% CI 不含 0。

系统命名：**A** dense-only + 论文配额 7/3；**E** dense 文本 + ColQwen 视觉 + 论文配额
（最接近论文的本地对照）；**D** RRF(BM25,dense) + 均衡配额；**G** RRF 文本 + ColQwen 视觉
+ 均衡配额（本项目最佳）。

### k=10

| 对比 | 池 | bge-small | bge-large |
|---|---|---|---|
| **G − E**　最佳混合 vs 论文式 | canonical | +0.0464* | +0.0453* |
| | selfbuilt | +0.0473* | **+0.0605\*** |
| **D − E**　全栈 vs 论文式 | canonical | +0.0362* | +0.0359* |
| | selfbuilt | +0.0371* | **+0.0511\*** |
| D − A　全栈 vs dense-only | canonical | +0.0452* | +0.0256* |
| | selfbuilt | +0.0461* | +0.0408* |
| D − C　配额叠加在融合之上 | selfbuilt | +0.0202 | **+0.0253\*** |

### k=20

| 对比 | 池 | bge-small | bge-large |
|---|---|---|---|
| G − E | canonical | +0.0027 | −0.0057 |
| | selfbuilt | +0.0074 | +0.0027 |
| D − E | canonical | +0.0008 | −0.0026 |
| | selfbuilt | +0.0055 | +0.0058 |
| **D − A** | canonical | **+0.0229\*** | +0.0060 |
| | selfbuilt | **+0.0275\*** | +0.0144 |
| **E − A**　ColQwen 视觉 vs 图片描述检索 | 两池同值 | **+0.0220\*** | +0.0086 |

（E − A 只涉及图片侧，与文本池无关，两池结果相同——可作一致性校验。）

### 三条结论

1. **头条结论没有被更强的基线吃掉，反而更强。** k=10 上 G − E 在 canonical 池
   基本不变（+0.0464 → +0.0453），在 selfbuilt 池**上升**（+0.0473 → +0.0605）。
   原因是对照臂 E 本身也用 dense 文本检索器，两臂一起变强；而 D/G 用的是
   RRF(BM25, dense)，更强的 dense 让**融合**受益更多。因此
   「提升来自弱基线」这一质疑，在 k=10 上不成立。

2. **一条已发表的结论必须撤回。** 「ColQwen 读像素优于在 VLM 描述上做检索」
   此前在 k=20 的 CI 不含 0（+0.0220*），换成 bge-large 后落到 +0.0086 且跨 0。
   它测的不是视觉表示的优势，是**文本检索器太弱**。同一个 k=20 上
   D − A 也从显著变不显著（两个池均如此）。

3. **k=20 从来就没有可主张的提升。** 四个池×模型组合下 G − E 与 D − E 全部跨 0，
   与 E27 早已记录的「只有 k=10 稳健」一致。更强的检索器没有改变这一点。

## 五、未完成：ColQwen 全池索引

机制已全部就绪并测试通过，但**索引本身只完成 5/220 篇文档**，因此
`eval_fullpool.py` 尚无可报告的结果。

原因是资源而非正确性：ColQwen2 权重需 4.49 GB，而本机 8.19 GB 显存中
Ollama 的 `llama-server.exe` 持有 3.26 GB，余下的放不下大图的激活；
且本会话每段只能运行约 9 分钟，而全量实测需要 5–9 小时 GPU。

已就绪的部分：

- `--image-source fulldisk` 从磁盘枚举全部图片（14,060 条 = 13,999 文件 + 61 别名，63.9/篇）
- `--doc-order random` 使**任何停止点都是文档的简单随机样本**，部分索引因此可报告
- 文档内检查点：单篇 660 张图的文档也能跨窗口续跑
- 分片以 `__b{batch}__` 命名并在载入时校验跨度
- `eval_fullpool.py` 只在**已索引文档**上估计，不把未索引文档的 gold 计为 miss

续跑命令（显存空闲时可无人值守跑完）：

```bash
.venv-colpali/Scripts/python.exe -m retrieval.colqwen_index \
    --image-source fulldisk --doc-order random \
    --out retrieval/colqwen_scores_fullpool.sqlite
python -m retrieval.eval_fullpool
```

## 六、本轮可达与不可达

## 七、结论对表述的约束

即使完成本轮全部工作，仍**不能**写「优于论文配置」。可以写的是：

- 「相对**最接近论文的本地对照**（bge-large 文本 + ColQwen2-v1.0 视觉、
  论文配额、421/doc 文本池）」——这是配额、模态分工、检索器族名都对齐，
  仅版本与解析流水线不可确定的对照。
- 若 (A) 的 ColQwen 全池 recall 落在论文 Table 6 的量级内，
  可以额外声明**本地 ColQwen 实现通过了量级检查**——这是实现验证，
  不是「复现了论文系统」。
