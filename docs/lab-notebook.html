E8立项依据被推翻

oracle 增益：看起来是机会，其实是测量结构的产物

仓库里有 19 个模型的 pure-text / multimodal 成对 response，覆盖同一批 2000 题， 所以「每题哪种输入更好」是已知的，零成本。

这个推断是错的

per-question oracle 增益大，不等于存在可路由的空间。 选取两个含噪声测量中的较大者，本身就会产生正增益。 对照实验：把同样的 oracle 用在两个不同模型的同一种模态上（匹配同一 |ΔF1| 区间）， 增益是 +9.0——与跨模态的 +8.7 无异。这个增益不是模态特有的。

粒度 × 预算：固定 top-k 与固定 token 预算给出完全相反的粒度排序

单位与覆盖范围已修正 · 见 E28

本条目所称「固定 token 预算」中的 n_tok 来自正则词元 [a-z0-9]+(?:[.\-][a-z0-9]+)*，不是生成模型的 BPE token。 全部相关表述应改为 word-like retrieval budget，或用最终生成模型的 tokenizer 重算——后者更可取，因为 proposal §13 的成本论证依赖真实计费 token。

本实验只覆盖 text gold + BM25 + 字符切分，未覆盖视觉 region/page、 parent section、稠密检索与下游生成。因此不能宣称「RQ3 已完成」， 应表述为「RQ3 的文本-BM25 切片已完成」。趋势结论（两个轴给出相反排序）不受影响。

① 两个必须先拆掉的陷阱

直觉设计是「各粒度各自映射 gold，比 recall@k」。这个设计被双重做局，两处都得先拆：

  • gold 的定义会随粒度移动。quote_corpus.map_gold 把每条 gold 指派给 覆盖它最多、且覆盖率 ≥50% 的单个 chunk。2,400 字符的 chunk 能整口吞下 334 字符的 gold（覆盖率 1.0），100 字符的 chunk 最多覆盖三分之一，直接记为未映射。 实测映射率：t100 94.13% / t300 96.86% / t600 97.84%——粗粒度在开跑前就赢了。 所以本实验完全不用 gold_map，改测「检索集合的 8-gram 并集对官方原始 gold 的覆盖率」， 目标在各臂之间完全相同；粗粒度只是更容易一口吃下，细粒度则要多花几个槽位去拼——那正是它该付的成本。
  • recall@k 不是公平的轴。10 个 2,400 字符 chunk 是 24,000 字符上下文， 10 个 100 字符 chunk 只有 1,000。粗粒度的 recall 是拿细粒度没拿到的上下文买来的。

可复现运行系统：把「终端里见过的数字」变成落盘产物

③ 顺带修掉的三个静默失败

分母静默缩小。eval_colqwen.py 里的 if eid not in set(eids): continue 今天一次都不触发（已由 verify E24 断言），所以已发布数字不受影响。但它是个定时炸弹： 一旦某次重建的池缺了 gold，recall 会因为难题悄悄离开分母而上升，且没有任何提示。 现在分母由全部视觉 gold 构成，池外 gold 计为 miss，覆盖率不足时默认拒绝出数。

这个修复是可验证的，不是理论上的：把 40 道题的 ranking 抽掉后， 旧口径仍会报 ColQwen Recall@20 = 0.9294（那 39 题直接消失了）， 新口径报 0.9149——因为它们被计为 miss 而不是被删掉。

读不出的图片被吞掉。colqwen_index.py 的 except: pass 会让某篇文档静悄悄地少索引几张图，而评测端仍按完整池计算。 现在每个失败写入 colqwen_failed_images.jsonl（含路径、是否存在、异常类型）， 结束时汇报数量并提示先跑 verify。

shell=True 与 Unix 命令。旧 runner 把格式化后的字符串交给 shell=True，在 Windows 上走 cmd.exe，引号会被改写，记录下来的命令 未必能原样重放。现在一律 argv 数组 + shell=False。 E29 注册表里的 cp 是 Unix 命令，本机根本跑不了，改用 make_eval_jsonl --out 直接写目标路径。

④ 花钱的路径：先用 mock 验证，再谈真实调用

API 调用是本项目唯一不能免费重来的操作，所以它的日志是一等产物而非调试辅助。 每次尝试（包括失败）都逐条 flush 落盘，含 token usage、provider request id、 HTTP 状态、rate-limit 详情与延迟。

resume 键的是 request_hash，不是 q_id。哈希包含实际展示的 quotes， 因此同一道题在不同检索配置下是不同的请求——实测 E29 的 paper 臂与 ours 臂 在 50 道题上哈希碰撞为 0。只按 q_id 续跑会把 paper 臂的答案当成 ours 臂的， 而那正好会让端到端比较失去意义。

本次没有发生任何真实 API 调用：全部用 --mock 的确定性假 provider 验证。测试覆盖成功、500 失败、429 限流、硬杀后的残行、以及 --force。 密钥过滤有一个值得记的坑：最初的正则用了裸 token，把 input_tokens 一起打成 <redacted>——而 token 数正是 唯一实测的成本量。正则已收紧并加了断言。价格一律标 price_verified: false。

① source.patch 还原不了这个仓库

git diff HEAD 只看得见 Git 已跟踪的文件。 而本项目 25 个被指纹覆盖的源文件里，有 18 个从未提交—— experiments.py、整个 expkit/、 retrieval/nested_cv.py、retrieval/ablation.py…… 也就是说，指纹能判定源码是否相同，却产生不出跑过的源码。 这正好是一份源码记录一半的用处。

对基准 run 20260828T080756Z_replay 实测： commit + patch 只还原 7/25 个文件，其余 18 个缺失。 这不是理论隐患，是量出来的。

现在每个 run 生成 source_bundle.zip：按原相对路径存放 manifest 中 全部源文件的字节，tracked 与 untracked 一视同仁。manifest 记录 bundle 的路径、 SHA-256、文件数，以及每个成员的路径、大小与哈希。 bundle 只含源码——数据集、模型、向量、索引、API 日志、response 与任何凭据形状的路径都被构造性排除，写入时再按路径二次校验。 patch 保留，因为它仍然是已跟踪文件改动的可审阅形式； 但它不再被宣称能单独还原一次运行。

还原步骤作用覆盖
git archive --format=zip <commit> 取出提交时的树。只读——在这棵常年脏着的工作区上 git checkout 会销毁数月未提交的工作 419 个已跟踪文件
git apply source.patch 已跟踪文件的工作区改动 7 / 25
unzip source_bundle.zip 权威：覆盖为真正跑过的字节 25 / 25

每次 run-suite 结束时会当场执行这套还原：在 artifacts/test-runs/ 下重建一棵树、重算全部源文件哈希， 结果写进 run.json 的 reconstruction_test 与 summary。 记录与它的证据一起出厂，而不是把证据留在一个可能没人跑过的测试里。

独立测试 tests/test_source_bundle.py 还会故意把 bundle 弄坏两次： 删掉一个 untracked 成员（别处无法补上）、改坏一个 tracked 成员 （证明验证器信的是 bundle 而不是 patch）——两次都必须 exit 1。 一个不会失败的检查不是证据。

过程中真抓到一个静默失败。git apply 会从当前目录向上寻找仓库； 当还原目录位于本仓库内部（默认就是，因为树建在 artifacts/test-runs/ 下）， 它会找到本仓库，认为改动已经存在，打印 Skipped patch 'eval_all.py'. 然后退出码 0。 一个报告成功的空操作比失败更糟。已用 GIT_CEILING_DIRECTORIES 切断向上查找，并改为检查它实际做了多少活，而不是只看退出码。

① 动作空间与两种货币

逐题路由：图片侧的「要不要看像素」可学，文本侧的「要不要融合」不可学

① 两条级联，八格，一个 Holm 家族

主对照必须是同预算下的随机分配。 「比不升级好」是废话——升级本身就多做了检索。 唯一能证明路由器懂 query 的，是它在同样预算下胜过随机挑谁升级。 B=0.50 事先声明，八格（2 级联 × 2 池 × 2 预算）一次算完做 Holm。

② 成本要按增量记，沉没的那一遍不退款

gpu 级联首轮跑了 bm25 图片描述，升级时改用 ColQwen—— 那一遍白做了但已经付过。所以升级的增量是 +1 cpu +1 gpu， 级联在 B=1 时是 3 cpu + 1 gpu，比直接跑静态系统（2 cpu + 1 gpu）更贵。 把「从零跑两个动作的成本之差」当增量会漏掉这一点。 成本参照系是静态系统，不是 B=1 的级联。

路由器在 B=0.05~0.15 就追平「总是用 ColQwen」的质量： 2.05~2.15 cpu + 0.05~0.15 gpu，对比静态的 2.00 cpu + 1.00 gpu。 省掉 85%~95% 的 GPU 遍历，多付 2%~7% 的 CPU。 两种货币不相加，所以这句话只能这样写，不能写成「省了 X%」。 而且这个 B 是看着曲线读出来的，属描述性数字，不是检验。

③ 把特征组也放进折内选择之后，强度掉下来

上面的 3/4 是把特征组事先固定为低维组（池形状 + 首轮分数）得到的， 而那个组是我在一格上试出来的——这本身就是一次选择。 把特征组连同模型族一起放进每个训练折内选，主家族只剩 1/8 存活 Holm， gpu 四格点估计仍全为正（+0.0015 ~ +0.0102）、两格 raw 显著； cpu 四格则落到 −0.0016 ~ +0.0043（capture −2.1% ~ 7.1%），依旧是零。

原因是内层目标在 1,200~1,600 条训练样本上选不稳特征组： 40 个 fold 里换了 5 种组合，其中 6 次选中含 384 维句向量的组。 这是 E23 的教训上升一层——不只是「别把句向量拼进去」， 而是「在这个样本量下，连该不该拼进去都选不准」。

因此可辩护的写法是：方向一致，强度取决于特征组是否事先固定，两种口径都报。

RQ1b 的 R² 目标问错了：把它推到完美，也只多买到 +0.014 recall

proposal 给 RQ1b 设了一个 R² 目标，并点名三个未试的特征源： 视觉检索器分数、模型内部表示、LLM 证据充分性判断。 E23 把测试 R² 从 −0.155（384 维句向量）抬到 +0.136（22 维分数+首轮观测） 就停住了，只留下一句「分配收益仍是 0~2%」。 于是有个明摆着没答的问题：究竟是 R² 太低所以值得换特征源， 还是 R² 到检索收益的映射本身就是平的？ 只有在前一种情况下，为新特征源花钱才合理。

① 与其争论，不如把曲线量出来

E21 已经确认天花板是真的：按真实模态比例分配能兑现 37%~45% 的 oracle 空间。所以问题纯粹是预测误差。做法是对一格目标 R² 造一个 无偏合成预测器 p = v + N(0, σ²)，测它买到多少。

两处刻意取最乐观，因此每一行都是天花板而不是预报： 合成预测器无偏、误差与真值独立（真实 ridge 会向训练均值收缩， 误差与真值相关，同一 R² 下严格更差）； 收缩系数在测试集上选，任何可部署系统都做不到。

② 两处必须踩对的实现细节

闭式解 σ² = (1−R²)·Var(v) 在这里是错的。 visual_share 大量堆在 0 和 1，把预测值裁到 [0,1] 会消掉很大一部分注入的误差， 名义目标 0 的实测 R² 落在 0.29——那会把 E23 的 0.136 悄悄放到曲线三分之二高的位置上。改成对**实测** R² 二分反解 σ 之后， 横轴才名副其实。

各目标点要用共同随机数。每个目标独立抽噪声时，每点带 ±0.001 的 蒙特卡洛噪声，足以让曲线非单调（0.136→0.200 反而下降）， 诱使读出并不存在的次序。改成同一批标准正态只按 σ 缩放之后， 沿曲线的差是配对的，两个池都单调了。

横切：反复出现的方法学教训

L1 · oracle 增益不等于可路由空间

出现在 E8。选两个含噪声测量的较大者本身产生正增益。 凡报告 oracle 上界，必同时报告同类系统之间的参照水平。

L2 · 粒度决定模态问题是否可见

出现在 E13/E14。页粒度把图和它周围的文字捆在一起，模态问题被掩盖； quote 粒度才让它显现。报告任何模态结论都必须绑定粒度。

L3 · 长度与池组成是最常见的两个混淆

出现在 E15。长文档天然包含更多查询词；同模态竞争者少的一方天然排名靠前。 做模态比较前先控制这两项。

L4 · 供应商报告的数字未必是同一个东西

出现在 E10。Gemini 的 in_tok 不含图片 token。 跨供应商用计费量做成本比较前，先做量纲合理性检查。

L6 · 基线必须和被比较者拿到同样的信息

出现在 E16→E17。我拿 RRF 去跟「按模态分别取最优」的固定检索器比， 等于偷偷给了基线 gold 模态的先验，于是得出「融合不管用」的错误结论。 比较双方可获得的信息必须对齐，否则赢的那一方只是拿到了更多先验。

L7 · 效应会随聚合层级稀释

出现在 E16→E17。检索器优势在证据条目层是 ±0.09，到查询层只剩 ±0.025， 因为 61.9% 的问题同时需要两种模态的证据。 决策发生在哪一层，效应就必须在哪一层测量。

L8 · 「结构存在」与「结构可观测」是两件事

出现在 E9 与 E19 的对比。E9 里排列/同类对照复现了全部增益，说明结构本就不存在； E19 里排列对照崩掉 0.104，说明结构真实存在，但三种策略都只拿到 4%。 报负结果时要说清是哪一种——前者是问题问错了，后者是特征不够。

L9 · 目标函数平坦时，argmax 会输给固定值

出现在 E19。最优点附近 ±2 个槽位只差 0.005，而含噪预测的 argmax 标准差达 5.6 个槽位。 先看目标函数的平坦程度再决定用不用 argmax 策略；收缩是标准解法， 而收缩曲线呈倒 U 本身就是诊断证据。

L5 · 改进语料会改变结论，这是对的

出现在 E12。补 OCR 提升了语料质量，同时消解了 RQ1b 原本的立论。 不能为了保住论点而拒绝改进；该做的是修正论点。

L11 · 基线必须真的复现被比较的那个系统

出现在 E27 / E28。本项目把一个「bge-small 同时跑文本与图片文字描述」的本地系统 标为「论文发布配置」，据此宣称提升。补上论文真正用的视觉检索器后， 六格显著缩到只剩 k=10 一格稳健。 凡要主张「优于已发表工作」，必先逐项核对基线身份：模型名与版本、 每个模态各用什么检索器、候选表示是像素还是文字描述、配额、池规模。 任何一项对不上，就命名为 local surrogate baseline，并另建最接近论文的对照—— 更强的基线通常会吃掉大部分表观提升。

L12 · 重采样单位必须是真实的抽样单位

出现在 E27 / E28。396 道测试题只来自 55 篇文档，同文档题目共享证据、文风与难度。 按题 bootstrap 得到的区间过窄，改按文档聚类后「融合单独贡献」在两个预算上失去显著性。 嵌套数据一律用 cluster bootstrap，并同时报告点估计、区间与聚类数（文档数）。 多个 k × 多个系统的比较要说明多重比较；CI 下界贴 0 不算显著。

L13 · 分母不能被静默改变

出现在 E27 / E28。映射失败的 gold 在评分集合形成之前就被 continue 掉， 于是永远不计为 miss，报出的其实是 conditional-on-mapped recall，绝对值偏高约 0.017。 不可检索的目标默认计为 miss；若要报条件口径必须单独命名。 每次评测强制打印 QA 数、文档数、gold 数、未映射数与丢弃数—— 这几个计数一旦常驻输出，这类错误当场就会暴露。

L14 · argmax 会在并列时悄悄制造结构

出现在 E19 / E28。recall 是小整数之比，最优配额常有长平台：97% 的题有多个并列最优， 中位 16 个。argmax 取最小索引，把一半以上的题判成同一个极端配置， 排列对照随之被推向极端，「查询特异结构」被高估一倍以上（+0.173 → 真实 regret +0.069）。 目标函数是离散比值时，先统计并列规模；报 regret 而非 oracle 减对照； 并报告「固定策略本身已最优的样本占比」——近八成时，可动空间只有两成。

L15 · 训练的标签必须就是你要的决策

出现在 E17 / E28。原实验训练 gold 模态标签、再写死「视觉→BM25、文字→dense」， 否证的是一条人工策略而非「逐题选检索器」本身。 改成直接以 recall(dense) − recall(bm25) 为目标后， 路由在符号上就不再输给固定检索器了（结论被推翻），只是仍输给融合。 用代理标签加人工映射得到的负结果，只能否证那条映射。 要否证一类方法，必须直接训练该方法的决策目标。

L18 · 约束下界是「最优固定策略」与「保配比置换对照」中更强的那个

出现在 E35。E19 里置换对照高于固定策略，E35 里反过来。 哪一个更强必须从数据读出来，不能假定；报 oracle 上界时两个都要给。

L19 · 预算实验的主对照是同预算的随机分配

出现在 E36。「比不升级好」是废话，因为升级本身就多做了检索。 只有在同样的预算下胜过随机挑谁升级，才说明路由器懂 query。

L20 · 级联的升级成本按增量算，沉没的首轮不退款

出现在 E36。首轮做了而升级用不上的那一遍已经付过钱。 用「从零跑两个动作的成本之差」当增量，会让级联看起来比它实际更便宜； 成本参照系是静态系统，不是 B=1 的级联。

L21 · 对照的期望能算就不要抽样

出现在 E36。均匀随机升级 m/n 时，第 i 题的期望恰是 base_i + (m/n)·gain_i。用几百次抽样去估它， 等于给唯一承载主张的对照加一层蒙特卡洛噪声—— 本实验里那点噪声足以让 Holm 校正后的 p 跨过 0.05。

L22 · 中间量被设成目标时，先测它取到完美时下游值多少

出现在 E38。proposal 给 RQ1b 设了 R² 目标，于是自然的下一步是去找更好的特征。 但正确的第一步是反过来问：R² 取到 1.0 时下游收益是多少？ 做法是造一个校准到目标精度的合成预测器扫一遍曲线， 而不是去猜新特征能带来多少。这里答案是 +0.023—— 整条曲线从「几乎无信息」到「完美」只有 +0.007 → +0.023， 映射本身是平的，所以 R² 目标问错了。 两小时的合成实验关掉了一整轮特征工程加一笔 API 开销。

L23 · 合成对照本身要校准，扫参数要用共同随机数

也出现在 E38，两处都会污染结论。 把预测值裁到定义域会显著改变实测精度—— visual_share 大量堆在 0 和 1，名义 R²=0 的合成预测器实测是 0.29， 足以把已达到的 0.136 悄悄放到曲线三分之二高处。必须按实测值反解噪声。 各目标点要共用同一批随机数，只按 σ 缩放； 否则每点 ±0.001 的蒙特卡洛噪声会让曲线非单调，诱使读出并不存在的次序。

L24 · 切片在选择之后做；异质性要用对照检验

出现在 E37。折外选择在全语料上完成一次，切片只划分已经算好的折外向量—— 让每个切片自己选配置，得到的就不是原实验的数字，而是 N 个各自过拟合的新实验。 而判断「提升是否依赖某一类问题」时，「一格显著、另一格不显著」不是差异的检验， 那是两个各自带噪声的判断之差，不是差的判断。要报两半之间的对照， 并且按文档 bootstrap——同一篇文档会同时贡献两半的问题。

L25 · 同一个量有六份实现时，要有测试断言它们一致

本项目六个模块各自带着一份 cluster_ci，实测区间逐位相同—— 但在 tests/test_statistics.py 之前，没有任何东西在看这件事。 若其中一份漂移成按题重采样、或漂移成「各文档均值的均值」， 受影响的实验会报出比数据支持的更窄的区间， 而仓库里每一项检查仍然全绿。 这类测试要断言性质而不是代码：注入纯文档效应时聚类区间必须变宽， 文档间无差异时不得变宽，100 题的文档不能与 2 题的文档等权。

L26 · 「检查点目录是空的」不等于「没有检查点机制」

正确的检查点实现会在工作单元完成后清理自己的分片， 所以空目录恰恰是它工作正常的表现。 我据此在交接文档里写下「文档内不能续跑」， 把一个随时可中断、随时可续跑的任务描述成了不敢开跑的任务， ColQwen 全池索引因此多搁置了一整轮。 判断续跑能力要去读代码或在运行中观察，不能从静态目录状态反推。
