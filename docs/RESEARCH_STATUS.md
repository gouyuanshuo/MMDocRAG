## 先把三个问题分开

1. **找得对不对？** 检索召回率（recall）：题目需要 4 条证据，检索找到 3 条，就是 75%。丢失或无法映射的证据也算没找到。
2. **引用选得对不对？** quote-selection F1：模型回答里引用了哪些片段，与标注的证据相比，既惩罚漏引，也惩罚错引。它不判断答案中的每句话是否正确。
3. **答案本身对不对、是否有依据？** 正确性和忠实度需要单独评价。例如模型可以引用对了图表，却读错图里的数字；也可以回答正确，却没有引用证据。

项目还有一个重要范围限制：主要评价是在**题目对应文档已知、候选证据已经建立**的条件下进行。它并没有证明在任意整库中先找对文档、再完成多模态问答的效果。

OCR 的旧记录也混用了“无文本”阈值。本次可复核的精确定义是**原始提取文本长度为 0**：补入已保存 OCR 后，零字符页从 1,486 降到 49（共 14,763 页）。这不是旧的“小于某个长度阈值”的指标，不能直接替换旧表里的 1,748 → 357 而不解释分母和阈值。

非劣检验的基本逻辑是“先定最多能损失多少，再判断区间是否排除更坏的损失”；不是观察 p 值后临时改口。参考 [Lakens 等的等效性检验教程](https://doi.org/10.1177/2515245918770963)与[非劣/等效性检验说明](https://lakens.github.io/statistical_inferences/09-equivalencetest.html)。这里采用双侧 95% 区间的下界，是保守的一侧非劣判据。

```powershell

```

续跑时要保持与原运行相同的 `--only` 选择；源码、输入或参数变了就开新运行。输出目录为 `artifacts/runs/<run_id>/`，看 `summary.html`；完整日志在 `artifacts/logs/`。查看历史数字时总是显式传 `--run`。

**这次验证的是当前工作区保存数据的复算。** 全新 clone 不含完整 PDF、图片、向量和所有私有 API 响应；不能保证只 clone 就免费重建一切。环境、数据恢复及昂贵重建的边界见 [REPRODUCE.md](../REPRODUCE.md)。历史 API 输出可重评分，但重新请求生成式模型不保证逐字相同。

代码需要整理，但不值得为“目录漂亮”大搬家。目前采用小范围整理：`reproduce.py` 是入口，`expkit/` 管运行和缓存，`retrieval/` 管检索实验，`router/` 管路由，两个 paired evaluator 管配对评价。历史脚本与产物路径保留，避免破坏数据对应关系。

## 距离 proposal 完成，还缺什么

**离线结果足以支持一个范围明确的课程研究报告，但不足以支持原题目里全部效率和忠实度承诺。** 最稳妥的写法是：以静态检索改进与路由负结果为已完成贡献，把 GPU 级联列为待验证的效率分支。

E39 已准备 `artifacts/e39/20260905/generation/plan.json` 及 static/routed/cheap 三套候选输入，600 题、220 文档、1,552 条 gold。主比较只需 static/routed 两臂，最多 1,200 次成功生成。旧 E29 使用不同检索器和配额，不能按相同题号直接复用它的回答。运行前要固定模型、thinking、预算与非劣界；当前 plan 明确写着 `prepared_not_generated`。

600 题沿用 E29 子集，**尚未为 2 点非劣界验证检验功效**。区间过宽时，结论应是证据不足，不能改大非劣界来让实验通过，也不能在反复查看结果后无规则地追加样本。

还做了输入去重检查：两主臂有 118 对输入完全相同，只有 **1,082 种不同输入**。若在生成前约定相同完整请求复用同一回答，可以省掉重复生成；另一种安排是生成 static 和 cheap 各 600 题，再按冻结路由合成 routed，这样 **1,200 种输入可以得到三臂**，还能检查路由相对 cheap 是否有价值。这个方案必须统一模型、prompt、thinking 和采样配置，并在生成前写入协议；当前只是离线检查，记录于 `request_reuse_audit.json`。

即使 E39 的引用 F1 通过非劣检验，也还不能自动证明答案更正确或更忠实。完整保留原 proposal 的话，需要额外冻结正确性/忠实度标注协议并做盲评；已整理好[可复用现有回答的评价协议草案](ANSWER_EVALUATION_PROTOCOL.md)。若还要声称能推广到新文档，则需要未用于方法开发的新文档或外部数据。不能再把看过的 split 改名为确认集。

效率报告还必须把 **CPU 遍历、GPU 图像检索、生成 token 和端到端时间**分开。这批 E39 的平均 CPU 遍历为 2.1967（静态为 2），GPU 检索为 0.1967（静态为 1）。少 80.3% GPU 调用不等于快 80.3%，也不等于省 80.3% API 费用；在线采集图像、写描述的前处理成本也没有被这些计数覆盖。
